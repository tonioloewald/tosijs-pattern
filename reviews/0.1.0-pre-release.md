## Blocker

### B1. indentedBlock scans blank lines without charging the step budget; `lines.push(...blanks)` throws RangeError (security, confirmed)

`src/engine.ts` ~437-490.

- **The defect:** `step(ctx)` is called only inside the per-character loop. On an empty line that loop never runs, and the outer per-line loop charges nothing.
- **Repro 1:** `fromJSON({kind:'indentedBlock'}).findAll('\n'.repeat(n), {maxSteps: 200000})`. It takes 125 ms, 478 ms and 1925 ms at n=5k, 10k and 20k, which is quadratic. At 40k it takes 8.4 s, and no `PatternBudgetError` is ever thrown.
- **Repro 2:** a parse over 100k blank lines is charged 5 steps.
- **Repro 3:** `pattern.text('a').indentedBlock().find('a\n' + '\n'.repeat(2e6) + '  x')` throws `RangeError: Maximum call stack size exceeded`. It should be a PatternError.
- **Why it blocks:** it breaks principle 4 ("every call has a step budget") on the untrusted fromJSON path. That is the library's stated purpose, and npm does not allow republishing a version.
- **Fix:** call `step(ctx)` once per line in the outer loop, blank lines included. Replace `lines.push(...blanks)` with a loop, or keep indices.
- **Check that clears it:** a work-counting test where `findAll('\n'.repeat(n))` under a small `maxSteps` throws `PatternBudgetError`, and where steps grow at least linearly with lines scanned. The test must fail with the fix reverted. Also a test that 2M blank lines does not throw RangeError.
- **Fix it with M1.** Close the class rather than patching each door: add a per-kind adversarial test, or a lint over `engine.ts`, asserting that every character-consuming loop charges `step()`.

## Fix before the tag (verified majors)

Each item is listed with the check that clears it. None of these needs a re-review.

### Correctness and security

- [ ] **M1. Delimited `columns()` scans without charging steps** (correctness + security, deduped; `src/engine.ts` ~436).
  - The last column's `while (...) at++` never calls `step()`.
  - `columns(['a'],{separatedBy:','}).text('!').findAll('x'.repeat(40000), {maxSteps:1e6})` takes about 1.3-1.4 s and never throws. `parse` of a 4000-char line reports `steps: 1`.
  - **Fix:** call `step(ctx)` per character in that loop.
  - **Check:** the findAll case above throws `PatternBudgetError`, and the reported steps grow with line length. The test is red with the fix reverted.
- [ ] **M2. A capture inside a `columns()` separator is silently dropped** (correctness; `src/pattern.ts` ~747).
  - `columns(['a','b'],{separatedBy: oneOf(',',';').as('sep')}).parse('1;2')` returns ok with `captures: {}`.
  - The cause: `checkCaptures` has no `columns` case, while `checkSkips` does have one.
  - **Fix:** add a `columns` case that checks `separator` the way list separators are checked.
  - **Check:** that call throws the "would be lost" error. Add the test beside the existing capture-loss tests.
- [ ] **M3. Replacement templates accept prototype names** (security; `src/pattern.ts` ~660).
  - `digits().as('n').replaceAll('a1','{constructor}')` returns `'afunction Object() { [native code] }'`. `{toString}` and `{__proto__}` behave the same way, and so does a pattern with no captures.
  - The cause: `name in m.texts` walks the prototype chain.
  - **Fix:** use `Object.hasOwn(m.texts, name)`.
  - **Check:** `{constructor}`, `{toString}`, `{__proto__}` and `{hasOwnProperty}` each throw the "replacement names …" error.

### Docs and efficiency

- [ ] **M4. Searches are quadratic for leading repetitions and for `until`, and the README safety section says the opposite** (efficiency + docs, deduped; README.md ~145, `src/pattern.ts` ~499).
  - Measured: `until(';').findAll('a'.repeat(4000))` and `letters().text('=').findAll('a'.repeat(5000))` both exceed the default 10M budget. `text('<!--').until('-->')` exceeds it at about 4 KB of `'<!--'`.
  - The README says "there is no catastrophic case".
  - **Fix:** add a sentence to "How it matches, and why it is safe" and to performance.md. It should say that find and findAll try each start position, so these shapes are O(n²) on text where they fail, and that they end in `PatternBudgetError`, never a hang. Point to anchoring (`startAt`/`startAfter` or a literal first step) and to #3750.
  - Add a step-count test that pins the current growth, so that the eventual fix shows up as a measured change.
  - **Check:** the sentence is present and the pinning test passes. The fix of the behaviour itself stays as work item 5.
- [ ] **M5. The README cannot be followed from npm** (docs; README.md ~14).
  - There is no install line.
  - All six examples import `tosijs-pattern/demo` (not exported and not in the tarball) and call `show(preview, …)`, which is undefined outside the site.
  - **Fix:** add `npm i tosijs-pattern`, plus one sentence that `show`/`preview` is the site's display helper and that `console.log` works the same way elsewhere. Or rewrite the examples' last lines so they run anywhere.
  - **Check:** paste the first example into a fresh project with the packed tarball installed, and it runs.
- [ ] **M6. The README Status says `0.1.0-dev … Not yet published`, and `llms.txt:1` says `v0.1.0-dev`** (docs; README.md ~163).
  - Both files ship, so the npm page would keep this text until 0.1.1.
  - **Fix:** in the release commit, update the README Status, llms.txt, package.json and the CHANGELOG heading together.
  - Also reconcile "Next: a look-behind piece": `startAfter` already ships (b540879).
  - **Check:** `grep -rn -- '-dev\|Not yet published' README.md llms.txt` is empty at the release commit.
- [ ] **M7. Four README links 404 on pattern.tosijs.net** (docs; README.md 71, 89, 165, 167).
  - The links are `docs-src/vocabulary.md`, `docs-src/from-regex.md` and `CLAUDE.md`.
  - **Fix:** use `https://pattern.tosijs.net/vocabulary/` and `/from-regex/`, and the GitHub URL for CLAUDE.md.
  - **Check:** every same-origin href in the built `docs/index.html` resolves to a page or file in `docs/`. Add this as a link check.
- [ ] **M8. from-regex.md ("Status: built") describes translator behaviour that does not exist** (docs; docs-src/from-regex.md ~56).
  - It claims structure recognition into `quoted`/`listOf`, but there is none.
  - It claims greedy `.*X` becomes `until`, but it is refused.
  - It says the `y` flag maps to "find at a position", but it is refused (`unsupported-flag`).
  - The census-plan text is stale.
  - **Fix:** separate what is built from what is planned, and correct the `y` row to "refused; use `find(input, { from })`".
  - **Check:** a test runs each row of the mapping table through `fromRegex` and asserts the documented outcome.

3. Install the packed `.tgz` in a scratch project under both Node and Bun, and import it. This smoke test replaces publish-smoke, which the manual path skips.
4. Optionally run release-doctor locally.
5. Run `npm publish --access public` with 2FA.
6. Configure the Trusted Publisher.

## Security record

*For ISO 27001 A.8.29 (security testing in development and acceptance).*

**Range reviewed:** `4b825dc642cb6eb9a060e54bf8d69288fbee4904...HEAD` (e838d70). This is the first release, so the whole tree is new: 49 files and 6,479 lines, excluding the generated `docs/` and `dist/`.

**How scope was derived:** the Tier 0 surface was stated by hand, because `tools/security-surface.ts` reported 0 files (the empty-tree base has no merge base). The surface is:
- the closure of `src/index.ts`: 11 files, all new;
- the manifests (`package.json`, `bun.lock`), with zero runtime dependencies;
- CI and publish (`.github/workflows/ci.yml`, `publish.yml`, `pages.yml`).

The library is itself a security boundary: it runs untrusted patterns where a regex engine is a liability.
